Sprint 0 · Architecture blueprint · 14 November 2026

School Intelligence OS

One shared record of priorities, actions, decisions, evidence and reviews sits at the centre. Every module reads and writes to it, so nothing is entered twice and each claim of impact can be traced back to its baseline.

Recommendation: build that shared core and the Leadership Command Centre first, on fictional data, with the assistant working from transparent rules. Add each specialist module as a new set of tables that link into the core. No application code has been written yet; this page is the plan for you to approve.

2 · System architecture

One application, separated layers, one database

What it is built with

Next.js, React and TypeScript for the application; Tailwind with shadcn/ui components for a consistent design system; Recharts for charts; React Flow for the curriculum dependency map; Drizzle for typed database access and migrations.

Why these choices

They are widely used, well documented and all free to run. A typed database layer means a change to one table is caught by the compiler everywhere it is used, which is what lets later modules be added without rebuilding the foundations.

How it is tested

Unit tests on the rules (what counts as overdue, how the assistant ranks work) and browser tests that click through each workflow end to end. A sprint is not reported as working until both pass.

3 · Database relationships

Four shared records carry everything else

Completion and impact are stored separately

An action has a status (to do, in progress, done). Impact lives on reviews, as demonstrated, emerging or not yet demonstrated, and a review can only be closed with evidence attached. The screens can then never show a finished action as proof that teaching or learning improved.

Fact and interpretation are stored separately

Each piece of evidence records what was seen and, in a different field, what it might mean. Evidence is also tagged with its place in the chain (baseline, implementation, change in practice, change in learning), which is what the Impact Observatory reads in Sprint 5.

8 · Data protection and responsible AI

No data breaches: hold little, expose nothing, prove it

No system can honestly promise that a breach is impossible. What the design can do is make one very unlikely and make sure there is almost nothing sensitive to lose if it happens. That is the standard this build is held to.

Breach prevention controls

  • Nothing sensitive to steal. No pupil names, no safeguarding records, no staff scores. Cohort and group totals only.
  • No real data until approval. Fictional data only until the data protection officer, IT and headteacher sign off. The import screen stays locked until then.
  • Code and data never mix. No data files, passwords or keys are ever saved in the code repository. An automated check blocks any attempt.
  • Private by default. The code moves to a private repository before Sprint 1. The application is never reachable without sign-in and is not placed on the public internet without approval.
  • School sign-in with two-step verification. Microsoft 365 accounts, so access ends when a staff account is disabled.
  • Encrypted in transit and at rest, hosted in a UK region, with encrypted backups and a tested restore.
  • Every access is logged. The audit log records who viewed, changed or exported what, and exports are off by default.
  • AI never sees identifiable data. Off until Sprint 7; then only minimised, non-identifying text, through one approved provider that does not train on it.
  • A plan if something goes wrong. Suspected incidents go to the data protection officer immediately, so the school can meet the 72-hour reporting duty to the Information Commissioner where it applies.

Cohort level first, never pupil names

Most gap analysis works on cohort, class and group totals. The database is designed to store those, and pseudonymous pupil codes only if a later decision requires them. Names stay in Insight and the MIS.

No safeguarding records, ever

Safeguarding concerns stay in the school’s existing recording system and procedures. The application has no field for them and the assistant will not analyse them.

Monitoring describes practice, not people

Findings are recorded by year group, phase and teaching practice. There are no teacher scores or rankings. Coaching notes about a named colleague are restricted to you and kept apart from appraisal. This needs agreeing with your headteacher before Sprint 4.

The assistant proposes; you decide

Every suggestion is stored as proposed until you approve or dismiss it, with its reasons and the records it drew on. Nothing is sent to another person, and no judgement about a pupil or colleague is made, without your action.

9 · Current guidance that shaped the design

What the plan takes from each source

Dates and status were confirmed by web search on 14 November 2026. GOV.UK and the EEF site could not be opened directly from this build session, so check exact wording at the links before quoting it.

  • Statutory (UK GDPR) and DfE guidance. A data protection impact assessment is required where processing is likely to be high risk, and the DfE advises involving the data protection officer from the start of any new tool. This is why real data is gated. Data protection in schools · Procuring EdTech
  • DfE standards (non-statutory). Generative AI: product safety standards, first published January 2025 and updated 19 January 2026. They are written mainly for pupil-facing products; this tool is staff-only, but their data protection and human oversight expectations are the benchmark used for Sprint 7. Product safety standards
  • EEF guidance (non-statutory). A School’s Guide to Implementation was substantially revised in April 2024. Explore, Prepare, Deliver and Sustain remain, but are treated as less linear, with more weight on engaging and uniting staff and reflecting at every phase. The improvement board therefore lets projects move backwards and builds in a reflection point at each stage. EEF implementation guidance
  • Ofsted framework. Report cards and the inspection toolkit have applied since 10 November 2025, with toolkit version 2.0 in use from 7 September 2026. Evaluation areas include inclusion, curriculum and teaching, and achievement, which map closely to your three priorities. Ofsted has said it does not expect written evidence against each toolkit standard, so the application is designed to run improvement work, not to produce inspection paperwork. Education inspection framework

Where I would challenge the brief

  • Nine modules against two to three hours a week is the main risk. Each module after the Command Centre should earn its place by saving time in the first fortnight of use; if one does not, stop building it.
  • Insight already analyses attainment. Sprint 3 should import its summaries and add the gap-to-response-to-reassessment loop that Insight lacks, and should not rebuild its reports.
  • The curriculum dependency map is the most valuable feature and the most labour-intensive to populate. Start with one strand in one key stage (for example, sentence construction in Years 3 to 6) and judge its usefulness before entering the rest.
  • A bespoke tool is a hypothesis. Its own impact should be reviewed after a term: time saved, gaps identified earlier, reviews completed on time.
